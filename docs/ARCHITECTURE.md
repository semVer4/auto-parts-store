# Архитектура

## Поток данных

```text
React UI → /api/orders → Netlify Function → валидация + серверный каталог
                                       → хранилище Netlify Blobs
```

SPA работает через Vite и React Router. Клиент отвечает за интерфейс, корзину и представление ответа API. Заказ считается созданным только после успешного ответа сервера.

Типы и правила статусов доступны в `src/shared/orders.ts`; серверный прайс — в `src/shared/catalog.ts`. Дублирование отображаемых клиентских полей не даёт клиенту права задавать цену.

## API

| Метод | Путь              | Назначение                                                 |
| ----- | ----------------- | ---------------------------------------------------------- |
| GET   | `/api/orders`     | Инициализировать демо-сессию, получить её заказы           |
| POST  | `/api/orders`     | Валидировать и создать заказ или вернуть результат повтора |
| PATCH | `/api/orders/:id` | Изменить статус своего заказа с проверкой версии           |

POST принимает `requestId`, `customer: {name,email,phone}`, `delivery`, `address`, `items: [{productId,quantity}]`. Денежные значения приходят из серверного каталога. POST возвращает `{order}`, а при повторе — `{order,replayed:true}`.

PATCH принимает `{status,version}`. Доступны `new → confirmed/cancelled`, `confirmed → shipped/cancelled`; `shipped` и `cancelled` терминальны. История содержит статусы и время изменений. Конфликт версии возвращает HTTP 409.

Ошибки полей возвращают HTTP 422, некорректный JSON — 400, превышение лимита сессии — 429, недоступность хранилища — 503. Ошибка не считается созданным заказом и не должна очищать корзину.

## Хранение и изоляция

Netlify Blobs — KV-хранилище, а не SQL-база. Состояние разделяется по непрозрачному случайному идентификатору сессии в HttpOnly-cookie. Пользователь не выбирает session ID в теле запроса. Список и операции доступны только для текущей сессии; общий список всех заказов не публикуется.

Вся ограниченная коллекция сессии хранится одним агрегатом с сильной согласованностью. Для первой записи используется `onlyIfNew`, для обновлений — `onlyIfMatch` с ETag. Это compare-and-swap: проверка повтора requestId, лимита и запись не расходятся по независимым ключам. POST повторяет конфликтующую попытку до четырёх раз, PATCH возвращает 409 при конфликте. Атомарность здесь относится к одной записи сессии, а не к внешним складу, оплате или другим коллекциям.

На сессию допускается ограниченное число заказов. Для автоматических unit/API-тестов используется in-memory repository; он не выдаётся за persistence опубликованного приложения.

## Защита и ограничения

- Сервер валидирует входные данные, наличие, количество и допустимые переходы.
- Ответы с данными заказа не должны кэшироваться общим CDN-кэшем.
- Изменяющие JSON-запросы ограничены своим origin; cookie не доступна JavaScript.
- В интерфейсе нужно использовать только вымышленные контакты. Наличие HTTP-валидации не делает приложение подходящим для реальных персональных данных.
- Сессионная cookie не является логином, MFA или системой ролей. Потеря cookie лишает посетителя обычного способа доступа к старым демо-заказам.
- Проверка версии, requestId и условные записи защищают конкурентные изменения внутри агрегата сессии. Это не заменяет проектирование транзакций между несколькими сущностями коммерческого магазина.
- Cookie действует семь дней; автоматической retention-очистки данных Blobs нет. Не используйте приложение для реальных персональных данных.
- Нет резервирования остатков, реального платёжного ledger, рассылок, SLA или полного аудита безопасности.

## Среды

Локально `@netlify/vite-plugin` поднимает Functions и Blobs рядом с Vite. Production-сборка лежит в `dist`, серверные функции обрабатываются Netlify. Статический preview полезен для UI, но не заменяет интегрированное API-окружение.

### Особенности локальной среды

- В локальном эмуляторе Blobs SDK 11.1.4 ответ GET может не содержать ETag. Адаптер в этом случае читает фактический ETag через `list` с точным фиксированным ключом, читает содержимое и проверяет неизменность ETag повторным `list`. Максимум три попытки; при нестабильном результате он отказывает в операции, а не делает безусловную запись. При наличии ETag в обычном ответе этот обходной путь не используется.
- Локальный эмулятор хранит данные в файловой системе и не является точной моделью production-конкурентности. Гонки бизнес-операций отдельно проверяются unit-тестами с внедряемым repository; production опирается на условные операции сервиса Netlify Blobs.
- Команда `dev` задаёт Node.js `--dns-result-order=ipv4first`, чтобы избежать ошибок подключения к IPv6 loopback в Windows. Это не отключает проверки API и не заменяет настройку сети production.
